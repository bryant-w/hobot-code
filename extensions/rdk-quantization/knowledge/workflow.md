# RDK model quantization workflow

Inspect the user model and data before choosing a configuration. Retrieve exact vendor deployment files and the upstream model card when available. Use the bundle, public command help, version output, compiler/runtime errors, official public source, and generated reports. Never read installed package implementation or private endpoint source code. For each unresolved semantic field, use at most two directly relevant public resources and stop when exact evidence resolves it. Write `quantization/task-spec.json` with concise sourced facts and unresolved fields before conversion. This file is a hard execution gate: version and help probes are allowed before it exists, but no command may invoke a compiler, converter, mapper, calibration stage, or build pipeline first. If one remote call must both prepare the workspace and compile, create and verify the task spec earlier in that same command. Preserve the original user model and data.

Establish model identity, input/output contract, preprocessing, stored calibration domain, floating model boundary, deployed runtime input representation, board interface, and matching platform template. Exact evidence may define facts; variant and family evidence are guidance only. Do not infer calibration normalization ownership from YAML names alone: reconcile the official calibration generator, local tensor statistics, and installed compiler behavior.

Probe the real compiler and board once each. Transform calibration only when confirmed necessary, print one stored-domain and compiler-domain tensor summary, and write a complete editable YAML from the matching template. When an exact official configuration matches the model variant and target platform, use it unchanged as the first baseline; a preference for precision, fewer conversions, or cleaner inputs is not evidence for overriding its runtime input type, preprocessing constants, calibration method, or compiler options. Change that baseline only after measured failure localizes one cause. YAML output and calibration paths are relative to the YAML file's directory.

Commands run with `set -e -o pipefail`. Keep optional probes in their own calls, or use `set +e` only around a probe and report its status. A failed or speculative compiler invocation still counts as conversion and therefore remains behind the task-spec gate. Keep setup, integrity checks, physical inference, and measurement independently observable. Retain settled facts in task artifacts rather than repeated prose. Compare materially different contracts only; choose the most directly applicable exact source before empirical validation.

Compile once with the best supported baseline and preserve the source model, YAML, and full conversion log. A compile self-check or x86 simulation is not physical-board evidence. Build a small evaluator from confirmed semantics, verify one sample and file count, compute floating references, and generate the declared board input representation with the exact official color order, numeric range, plane layout, and resize policy when available. Transfer one digest-verified archive, verify one physical output before starting the batch, and execute a physical board batch. Measure labeled task quality when annotations exist, output fidelity, model and end-to-end latency distributions, throughput, temperature, and resources.

After a failure, use at most two diagnostics to locate the first failing boundary, then change one coherent cause. Distinguish model conversion error from evaluator input encoding or runtime-interface error. Fix generated validation inputs without recompiling when conversion evidence is healthy and the mismatch is outside the floating model boundary. Do not retry a hanging or unchanged command. If quality or performance fails, adjust one justified cause and rerun the affected stages. Use no more than three total conversion attempts. When exact official preprocessing and one full validation comparison agree, stop testing equivalent alternatives. As soon as one physical candidate meets the declared acceptance requirements, stop optional diagnostics and finish the report.

Finish by reading `bundle://knowledge/report-schema.json`. Before writing the report, copy the final model, source model, exact conversion YAML, and complete conversion log to four distinct board-relative paths and verify their board digests. Then write `quantization/provenance.json`, compute its final digest, and write `quantization/report.json` last at the x86 task workspace with schema fields directly at the JSON top level. `artifact.path` is relative to the board task workspace. The report's `provenance` field contains exactly `path` and `sha256` and points to `quantization/provenance.json` in the x86 task workspace. That provenance document contains a top-level object named exactly `delivery`; put the three board-relative provenance file paths and three intervention booleans inside `delivery`. All five report, artifact, and provenance paths are distinct. If either JSON document is rewritten, recompute every affected digest after the final write before ending the turn. Pure PTQ and compiler-generated graph, preprocessing, lowering, or quantized representations are Tier A and leave `graphChanged`, `weightsChanged`, and `retrained` false.
